# Provenance and evolution design — before implementation

1. A source produces many ideas through Create idea from this source, including further discoveries later. Each creation stores a new idea, never another copy or edit of the source. Optional exact excerpts are UTF-16 half-open offsets into immutable source text; pasted excerpts must match uniquely, or selection supplies an unambiguous range.
2. Keep the existing required idea.source as the primary origin. Optional idea.provenance records {sourceId,start?,end?}; legacy records resolve to their primary source in memory without migration or writes. Additional origins can be attached, and a merge unions the contributing origins. Primary origins and existing excerpt references are retained.
3. Merge selects at least two existing, non-merged-away ideas. The user reviews complete content, metadata, comments, provenance and connections, chooses a survivor, and edits its text explicitly. One queued transaction checks every participant version, keeps all records, preserves contributor text/comments/relationships, marks away records Superseded, and adds immutable merge metadata {into,at,operationId}. The survivor's merge-completed history records contributors. No prose is generated; no compilation flags change.
4. Completed merges use merge metadata, not the legacy Merge disposition. Merge is displayed as Needs merge. Archive remains valid, readable and filterable but is removed from new primary choices. Legacy merged-into relationships remain readable as links, without falsely claiming a new atomic merge happened.
5. One canonical lineage edge is stored; incoming edges are computed. Supersedes means newer -> older, while merged-into means older -> survivor. Combined replacement direction (older -> newer/survivor) must be acyclic, including legacy merged-into links and actual merge markers. Supports/contradicts/related-to do not create replacement order and may cycle. A dedicated supersede action checks both versions, marks the old item Superseded, preserves both records and selection, and records events. Mere contradiction does not alter disposition.
6. A collapsed Sources & evolution surface answers origin, predecessor, successor and current-inheritor questions by clickable titles, with full source access. Source views list all ideas they contributed to, including merged-away records. Incoming/outgoing sections describe direction in words; no reciprocal data or graph canvas.
7. Optional per-idea history begins with actual new actions, never fabricated legacy history: creation, substantive title/summary edits, disposition and inclusion changes, relationships/provenance, completed merges and supersession. Timestamp, type, related IDs and useful before/after values are stored once per acknowledged change. No keystrokes, full event sourcing or automatic history pruning. Legacy items explicitly have no pre-upgrade event record.
8. Compilation remains editorial. Warn for included Trash, Superseded, merged-away items, and an included predecessor whose replacement is not included. Do not change inclusion automatically. Markdown names relationship targets and all contributing sources.

The persistence queue, writer ownership, revision/generation semantics, verified backups and local request checks remain in place. Multi-record evolution responses include each affected idea/version; client acceptance gains per-idea response ordering so a late older response cannot overwrite a newer multi-record result. New creation/merge/supersession intents are validated and committed through the existing transaction boundary, with required pre-operation backups for creation and multi-record operations. Source attachment uses the ordinary periodic-backup policy.

All mutation and browser tests use synthetic temporary ledgers. Protected hashes are private and compared at the end. No live migration, source rewriting, database/framework change, AI extraction/merging or generic knowledge-graph machinery.

## Implemented details and limits

- Schema stays at version 2. The existing field is named `source` in this application, and remains required. No read-time migration materializes optional fields. Export/import preserves new fields; older code is not safe to use for editing new evolution records.
- Excerpt offsets use JavaScript UTF-16 indices, not byte positions. Pasted CRLF/LF line endings are matched equivalently and mapped back to the verbatim source range. Repeated passages require selecting the intended occurrence in Full Source. Explicitly importing changed raw text still requires the existing replacement review; ranges are bounds-validated, not independently versioned.
- A completed merge does not move comments or existing relationships to the survivor. They remain on contributor records, reachable by title. Survivor origins are unioned; its previous text and metadata are recorded in history when changed. There is no one-click unmerge. Verified backups and retained records support deliberate correction.
- “Latest linked inheritor” follows explicit supersedes and merge replacement paths, potentially to multiple terminals. Refinement and derivation are visible as developments, but do not automatically declare the older idea obsolete. Legacy merged-into links participate in replacement ordering and are labelled as legacy/unverified rather than completed transactions.
- History records substantive title/summary, disposition, inclusion, relationship, origin, creation and merge/supersession changes. Comments remain editable context without per-keystroke history. Ordinary project/type/tag edits do not generate separate events; merge metadata changes do. History is not a complete event log or immutable audit system.
- Conflicting extraction/source-attachment drafts offer a two-stage review of fresh content before explicitly adopting its generation/version. Merge refresh retains the user's prose, shows fresh participants and clears confirmation. Missing-record drafts remain copyable/discardable. No uncertain operation is automatically replayed.
- `npm test`: dependency-free server/model/client regressions. `npm run test:browser`: optional Playwright/Edge browser regressions; set `LEDGER_PLAYWRIGHT_PATH` to an existing Playwright installation if it is not resolvable locally. Playwright is QA tooling, not an application dependency. Tests use temporary synthetic ledgers and verify disk/reload state.
